# 로봇팔 배송 미션 기획안 최종본 (규정 최우선, 사용자 확정 정책, Codex 12차 검토 승인)

## 0. 우선순위 원칙 [변경]
1) 명시된 규정 이행 → 2) 안전 확보 → 3) 감점 최소화. 규정에 근거 없는 사항은 **규정 문구를 그대로 따르는 확정 기본값(H절)**으로 정하고 구현·시험으로 입증한다. **"승인 보류" 상태는 없으며, 정상 경로와 3차 실패 경로는 항상 끝까지 실행되게 만든다.** 완료는 세 가지로 구분한다: **정상 배송 완료 / 3차 실패 후 주행 / 안전 중단**(하드웨어·저장 불가 등으로 로봇이 안전하게 계속할 수 없는 경우에는 억지로 진행하지 않으며, 이것이 "무조건 주행 완료"를 뜻하지는 않는다). **경기 중 사람의 제어 명령·색 입력·시작/재시작 신호·파일 수정은 금지하며, 규정이 허용한 "떨어진 공을 받침대 원위치에 놓기"만 허용한다(공을 놓는 행위를 동작 명령처럼 쓰지 않는다).** 확정 기본값대로 로봇이 자동 처리하거나 안전 정지한다. 심판이 경기를 중단하는 경우는 사람이 로봇에게 명령하는 것이 아니라 심판 절차로 분리(동작 명령·재시작 지시 없음).

## B. 정책
1. **시도 정의**: 시도 N은 "공을 집으러 내려가는 동작 시작"에서 시작한다. 같은 시도 안의 재촬영·재관측은 시도에 포함하지 않는다. **그리퍼 열기(놓기) 명령 이후 다시 공을 집거나 넣으러 내려가는 모든 동작은 새 시도**로 센다(보수적). (확정 기본값) 어떤 경로로도 총 3시도를 넘기지 않는다. **모든 시도(새 집기든 놓기 후 재넣기든)는 하나의 절차로 시작한다: 시도 수 증가 → 저장 성공 확인 → 그 뒤에만 해당 물리 동작 허용. 남은 시도가 없으면 하강 금지.** 색 재관측 횟수(`reobserve_count`)와 물리 시도 횟수(`physical_attempts`)는 별도 변수이며, 색 판정은 항상 결과를 내므로 시도를 소모하지 않는다(D3).
2. **시도 기록(영속)**: 확인한 주문 색, 누적 시도 수, 마지막 물리 동작, 결과를 파일에 저장. **집기 하강 명령 전에 해당 시도 시작을 기록하고, 저장 실패 시 새 집기 금지.** 재부팅은 시도 수를 초기화하지 않는다.
3. **실패 확정 증거표(고정)**: 
   - 집기 실패 의심: 닫은 뒤 개도가 공 크기 범위 밖(다 닫힘). 이것만으로 확정하지 않는다. **확정**은 추가 증거(빈 그리퍼 영상 + 공이 받침대 원위치/도로에 보임)가 함께 있을 때. 증거가 서로 모순되면 RESULT_UNKNOWN.
   - 넣기 실패 확정: 놓기 후 공이 바구니 밖(도로/받침대/그리퍼에 남음)에서 확인됨.
   - 성공 확정: 전후 영상 비교로 바구니 안 공 크기·형태·위치가 1초 이상 안정, 그리퍼엔 없음.
   - **결과 불명(RESULT_UNKNOWN)**: 성공도 실패도 증거가 없는 경우. 재관측 K회(시간 T_unknown 이내)로 결론을 시도하고, **그래도 성공을 확인하지 못하면 사용자 확정 정책에 따라 해당 시도를 "집기·넣기 실패"로 센다**(확정 기본값: 성공은 증거로 확인해야만 성공, 확인 못 하면 실패 시도 1회). 단 **중복 상차를 막기 위해 실패 처리 전에 먼저 판정**한다: 받침대 원위치에 해당 공이 없고 + 그리퍼가 비어 있고 + 바구니 밖(도로 등)에도 공이 안 보이고 **바구니 내부에서 공이 실제로 관측될 때에만** 성공(단순한 "공 미검출"은 공 존재 증거가 아니며, 받침대 뒤·차 아래 등 사각지대는 시험으로 확인), 받침대에 공이 그대로 있으면 집기 실패, 공이 바구니 밖에 보이면 넣기 실패. 이 판정에서도 불명이면 **실패 시도로 센다.** 불명 판정 자체는 제한 시간 안에 종료하며, 이후에는 실패 횟수와 공 위치에 따라 완료·복구 대기·안전 중단으로 전이한다(아래 분기 순서). RESULT_UNKNOWN 감지와 로그 기록은 항상 구현한다. **횟수 계산과 다음 동작 허용은 분리한다**: 다음 집기 전에 해당 공의 위치와 바구니 중복 여부를 먼저 확인하고, **원위치에 공이 없고 바구니 내부에서도 관측되지 않으면** 이는 "떨어진 공" 상황(규정 5)으로 보고 팔은 정지·대기하며 D6의 복구 조건(팀원이 공을 원위치에 놓음)을 기다린 뒤 다음 시도를 시작한다. **불명 판정은 발생한 그 시도 한 번만** 실패로 센다(하강 없이 남은 시도를 소모하지 않는다). 사람이 공을 꺼내거나 다른 공을 공급하는 경로는 없다. **fail_attempts를 통보하기 전에 반드시 바구니 내부를 확인**하여 성공이면 `ok`로 일관되게 통보한다(실패 통보 시험 필수). **정상 검증·불명 복구·실패 통보 직전 검증은 모두 하나의 성공 판정 함수**(공 형태·바구니 내부 위치·1초 이상 안정 + 빈 그리퍼)를 사용하며, 마지막 검사라고 조건을 생략하지 않는다. **분기 순서(재시작 복구에도 동일)**: 현재 시도 종료 → 공통 성공 검사 → ① 성공이면 완료 ② 실패이고 3번째 시도였으면 실패 통보(바구니 내부 확인 포함) ③ 실패이고 남은 시도가 있을 때만: 원위치에 공이 있으면 다음 시도, 없고 바구니 내부에도 없으면 복구 대기. **복구 대기 중에도 제한된 재관측으로 바구니의 공통 성공 검사를 수행**하며, 정해진 복구 시간(T_restore_max)까지 공이 돌아오지 않고 성공도 확인되지 않으면 남은 시도를 허위로 소모하지 않고 **안전 중단**으로 종료한다.
   - 3번째 시도에서 **실패가 확정**되면(증거 있음) 반드시 실패 통보 경로로 이동한다.
4. **색 판정(티칭 기반, 항상 결과를 낸다)**: 경기 전에 현장 조명에서 **티칭(기준색 등록)**으로 빨강·파랑 포스트잇의 기준 색값을 저장한다(D3). 판정은 두 기준색 중 가까운 쪽을 **강제 선택**하며(규정상 바구니 포스트잇은 빨강 또는 파랑 중 하나뿐), "판정 불가"·`obs_fail` 상태는 없다. 투표 비율은 기록만 하고 낮아도 선택은 반드시 한다(재관측은 정확도를 높이기 위한 것이지 선택을 거부하기 위한 것이 아님).
5. **자동차 출발 조건(3개 모두)**: (a) **현재 작업의 확정된 결과**(`ok` 또는 `fail_attempts`) + (b) **현재 작업의 유효한 `clear`**(실제 관절 위치를 읽어 대기 자세 도달을 확인한 뒤 발행, 성공/실패 동일, 고정 지연 없음) + (c) 자동차 자신의 상차 대기 상태. **ack는 출발 조건을 대신하지 않는다.** 장비 고장으로 못 빠지면 `status=hw_fault`만 보내고 `clear` 안 보냄(처리는 확정 기본값: 정지 유지, 사람 지시 없음).
5a. **clear 발행 뒤 차량 이탈 확인 전까지 팔은 검증된 대기 자세를 유지하고 자동차 이동 공간에 재진입하지 않는다.** **clear 이후 작업 재개 예외는 두지 않는다**(자동차 위치·방향이 바뀌었을 수 있고 이를 안전하게 되돌리는 기능은 이번 범위가 아님).
5b. **done→대기 복귀→clear는 ack와 무관하게 진행**한다. 재전송·ack 처리는 팔 동작과 별도 스레드/타이머에서 수행하며, 실제 ack를 받아야 대기 자세로 가는 조건은 두지 않는다. ack 유실·자동차 재시작으로 팔이 중간 자세에 무기한 머무르지 않는다.
6. **차량 정지 잠금**: 자동차가 정해진 상차 구역에 정지하면 **팔의 메시지 수신과 무관하게** 자동차 스스로 `clear` 전까지 출발 잠금(D와 합의 필수, 필수 조건). 팔은 도로가 보이는 자세에서만 차량을 감시한다.

## C. 상태 기계 · 부팅 구분 [변경]
- 콜드 부팅(전원 투입, 작업 파일 idle): BOOT_CHECK → WAIT_POSE.
- 재시작(작업 파일이 idle이 아닌 모든 상태, 또는 파일 누락·손상 — 상태별 행동은 D9 "부팅 행동표"): **먼저 작업 기록·현재 관절/그리퍼 상태를 읽고, 이동 없이 정지**한다. **자세·상태별로 사전 검증된 복구 경로만** 허용한다(걸림·접촉 여부와 현재 상태를 판별할 수 없으면 이동하지 않는 HW_FAULT로 남긴다). "먼저 위로 이동" 같은 공통 규칙은 쓰지 않는다. 자동 서비스 재실행도 이 경로를 따른다.
- 정상 흐름: WAIT_POSE → ARRIVAL_CONFIRM → READ_COLOR → ATTEMPT(n){OBS_STAND→PICK→LIFT_CHECK→PLACE→VERIFY} → 성공이면 RETREAT_MID → REPORT_DONE_OK → WAIT_POSE → REPORT_CLEAR → CAR_LEFT_CONFIRM → WAIT_POSE.
- 3회 실패: RETREAT_MID → REPORT_DONE_FAIL_ATTEMPTS → WAIT_POSE → REPORT_CLEAR → CAR_LEFT_CONFIRM.
- 별도: RESULT_UNKNOWN(재관측 후 실패 시도로 환산, 새 중복 상차 방지 판정 포함), HW_FAULT, ABORT_SAFE.
- RETREAT_MID는 **바구니에서 빠져나온 중간 자세**(대기 자세 아님). **RETREAT_MID에서 팔이 바구니와 완전히 분리된 뒤 상차 상태를 다시 확인**하고, 그때 `loaded_confirmed`를 저장한다(후퇴 중 공이 밀려난 경우 포착). **`revoke`는 두지 않는다**(이미 전달된 출발 허가를 통신으로 되돌릴 수 없고 지연 메시지가 재허가로 오인될 수 있음). **최종 재확인 후 완료 상태(`loaded_confirmed`/`failed_confirmed`)를 영속 저장하면 결과가 확정되며, `done`은 그 확정 결과의 통보이다. 확정 후에는 정정하지 않는다**(저장 직후 중단돼도 재시작 후 같은 결과를 보낸다. 결과를 고칠 일이 없으므로 결과 개정 번호도 두지 않는다). **`clear` 발행은 되돌릴 수 없는 작업 종료 지점**이다. 따라서 공 재확인과 필요한 수정은 **done 발행 이전에** 모두 끝낸다: `성공 확인 → RETREAT_MID → 바구니와 분리 후 재확인 → loaded_confirmed 저장 → done 발행(→ `done_published` 저장) → WAIT_POSE(이 자세에서의 바구니 관측은 **기록용이며 결과·행동을 바꾸지 않는다**) → `clear_committed` 저장 → clear 발행`. **재확인 단계(done 이전)에서 공 이탈이 관측되면** 같은 작업에서 시도 정의에 따라 처리한다(`loaded_confirmed`는 저장 전이므로 상태 충돌 없음). **done 발행 이후 발생한 공 이탈은 팔이 정정·재작업할 수 없으며 규정상 공 유지 실패(-10) 위험으로 본다.** 즉 `loaded_confirmed`/`failed_confirmed`는 "결과 확정"이며 그 이후 새 물리 시도는 어떤 경우에도 없다.

## D. 단계별 설계
### D1 부팅
점검: 포트, 모터 ID 1~6 ping, 온도, 카메라, 보정 파일, 작업 파일. 허용 시작 영역(휴식 자세에서 전원 투입, 확정 기본값) 밖이면 자동 이동하지 않고 경고. 저속 이동. 시야 영상 기록.
### D2 도착 확인
정지 구역 ROI, 바구니 존재 확인(실제 바구니로 1일 차 검증), 포스트잇 영역 크기·종횡비·위치, T_stop 초 연속 정지. 경계 불확실하면 색 판정 시작 안 함. 빈 도로·횡단보도 위 차·부분 진입·그림자 시험.
### D3 색 판정
**티칭(기준색 등록)**: 경기 전에 현장 조명에서 빨강·파랑 포스트잇(심판이 쓸 실제 종류)을 그리퍼 카메라로 비추고 기준 색값(HSV 범위/중심)을 저장한다. 조명 4조건(밝음/어두움/반사/부분 가림)마다 추가 티칭 가능. 판정: 바구니 ROI 안 포스트잇 영역의 색을 프레임 투표로 두 기준색과 비교해 **가까운 쪽을 강제 선택**(항상 빨강 또는 파랑이 결정됨). **먼저 포스트잇의 위치·형태로 주문 영역을 정하고, 그 영역 안에서만** 빨강/파랑을 선택한다(주변 공·바구니 색의 면적이 주문을 결정하지 않으며 시험한다). 거리 계산: 색상(원형 거리)+채도 가중으로 두 기준색까지의 거리를 구하고, 프레임 투표 동률은 거리 합이 작은 쪽, 그래도 동률이면 로그에 남기고 고정 기본값으로 선택. 선택 전에 제한된 횟수(N회)의 노출 조정·다른 자세 관측을 자동 수행한다. **검증 지표는 "항상 출력함"과 "맞게 읽음(정답 일치율)"을 분리**하여 기록한다. **티칭 경계**: 빨강·파랑 기준색은 **주문 배정 전에 둘 다 등록·검증하고 설정을 고정**한다. 주문 배정 후에는 설정을 고치지 않으며, 티칭 화면·설정에 현재 주문을 지정하는 기능을 두지 않는다. 재관측은 자세를 소폭 바꿔 정확도를 높이는 용도. 관측 자세마다 ROI·임계값 분리, 카메라 이동 중 프레임 폐기.
### D4 집기·확인
OBS_STAND에서 공 확인. 닫은 뒤 개도 범위, (읽을 수 있으면) 부하, 짧게 들어 유지·재확인. 실측 불가한 센서는 설계에서 제외.
### D5 넣기·확인
above_basket → basket → 열기 → 후퇴. 전후 영상 비교(포스트잇 영역 제외, 공 크기·형태·위치, 1초 잔류). "공 없는 바구니+포스트잇" 오인 시험 필수.
### D6 공 복구 (팀원은 공만 원위치)
복구 대기 자세는 **사람이 공을 돌려놓는 경로 밖**으로 정한다(1일 차에 해당 자세에서 받침대·공 위치가 카메라에 보이는지 실물 확인). 재개 조건: 해당 색 공이 원위치에서 N초 안정 + **허용된 고정 물체와 그 공을 제외한** 추가 물체·사람·움직임이 보이는 영역에서 T_quiet 초 연속 없음 + 팔의 접근 경로 전체가 실제로 관측 가능함이 1일 차에 입증됨. 입증되지 않으면 **복구 대기 자세·관측 구성을 바꿔 입증될 때까지 조정한다**(승인 보류가 아니라 구현 과제). 입증 전에는 팔은 정지 유지하며 사람 지시 없이 카메라 조건만으로 재개한다.
### D7 통신
- 식별자: `boot_id`(부팅마다 새 값)와 `job_id`(**재부팅을 넘어 유지**, 작업 파일에 저장, 상차 작업 1건당 1개)를 구분. **job_id 생성 주체는 팔**: 카메라로 도착을 확인(D2)한 뒤에만 새 job_id를 만든다. **수락 주체는 자동차**: 자동차는 이미 상차 대기(출발 잠금) 상태일 때만 그 job_id를 수락하고, 과거·이미 완료된 job_id는 거부한다. 팔 재시작: 작업 파일의 job_id 유지. 자동차 재시작: 자동차가 hello를 보내고 팔은 현재 job의 단계를 재발행하며, 자동차는 상차 대기 상태 재진입 후에만 수락. **이 통신이 팔의 카메라 자체 감지를 대신하지 않는다.**
- **자동차 쪽 영속 상태(D와 합의, 필수)**: `load_wait → result_received → release_allowed → left_zone`을 저장. 결과를 수신하면 **먼저 영속 저장한 뒤에 ack**한다. **같은 job_id가 진행 중이거나 복구 중이면 거부하지 않고 이어받는다**(완료된 job_id만 거부). 자동차 재시작 후 hello를 보내면 팔은 현재 job의 **확정 결과와 현재 안전 상태 전체**를 다시 보내고, ack는 자동차의 현재 `car_boot_id`를 담아 재접속 시 다시 받는다. 팔은 ack를 받았어도 자동차의 `car_boot_id`가 바뀌면 결과·상태를 재발행한다. **자동차는 재시작 후 결과·job_id는 복구하되, 저장된 `release_allowed`를 그대로 실행하지 않는다.** 출발 실행 권한은 재접속 절차에서 **현재 팔의 안전 상태를 다시 확인한 새 clear**(현재 `arm_boot_id`·`car_boot_id`와 일치)를 받은 뒤에만 부여하며, 부팅 식별자가 바뀌기 전의 오래된 clear는 현재 확인으로 인정하지 않는다.
- 전달 보장: `done`과 `clear`는 한 번 보내고 끝내지 않는다. 현재 job의 결과 단계를 **자동차의 단계별 ack를 받을 때까지** 1 Hz 상태 메시지에 포함해 재발행. ack는 `(job_id, step=done|clear)`를 담는다. 재시작 후 `clear`는 관절 위치로 안전 자세를 다시 확인한 뒤에만 생성(과거 clear 자동 재발행 금지).
- 토픽 예: `/arm/state`(1 Hz, boot_id/job_id/단계/결과), `/arm/status`(hw_fault, abort), `/car/ack`. 메시지 타입 std_msgs.
- 시험: 부팅 순서 반전, 한쪽 재시작, 지연·중복·유실 메시지, 메시지만 있고 차 없음(시작 안 함), 차만 있고 메시지 없음(정상 시작).
### D8 과열·센서
장비 데이터시트의 허용 한계 확인 후 실측으로 여유 검증. 1일 차 확인 항목마다 "없으면 대안"을 정해 두고 **그 대안으로 계속 진행한다**(예: 부하값을 못 읽으면 개도+영상으로 확인. **관절 위치를 못 읽으면 clear를 만들 수 없으므로 통신·모터 점검으로 반드시 읽히게 만든다**. 온도를 못 읽으면 최악 부하·주변 온도에서 검증한 동작/휴식 시간표와 **경기 중에는 토크를 유지**한 채 대기 자세의 저부하 상태로 열을 관리한다. 토크 해제는 경기 밖의 지지되는 휴식 자세에서만). 경고: 새 시도 보류, 진행 중 안전 동작만 마무리. 중단: 이동 시도 없이 정지 후 hw_fault. 토크 해제는 물리적으로 지지되는 휴식 자세에서만(대회 중엔 유지).
### D9 작업 파일
**한 작업 기록(같은 레코드)에 `job_id, color, physical_attempts, last_action, phase, done_published, clear_committed`를 항상 유지**하고, 완료는 새 파일 형태가 아니라 **같은 기록의 `status` 변경**이다: `status ∈ idle | in_progress | motion_unknown | loaded_confirmed | failed_confirmed`. 완료·재시작으로 color·physical_attempts를 잃지 않으며, 네 번째 시도는 불가능하다. 성공·3차 실패는 모두 **영속적인 완료 결과**로 저장하며, 완료 후에는 새 물리 시도를 금지하고 결과 전달·안전 복귀·clear·차량 이탈 확인만 수행. in_progress 재시작 시 새 집기 전에 현장 재관측(RESULT_UNKNOWN). 완료 상태는 CAR_LEFT_CONFIRM 후에만 idle. 시도 기록 직후·하강 전 정전 등으로 **동작 수행 여부가 불명확하면 `motion_unknown`**으로 두고 그 시도는 소모된 것으로 센다(확정 기본값). **저장은 임시 파일 작성 → 디스크 반영 → 원자적 교체 + 체크섬**으로 하고 손상 시 `motion_unknown`/HW_FAULT. 수동 리셋은 개발 모드 전용(대회 빌드에 포함하지 않음).
**부팅 행동표(저장 가능한 모든 상태)**:
| 저장 상태 | 부팅 후 행동 |
|---|---|
| idle (정상 파일) | 콜드 부팅 경로: 점검 → WAIT_POSE |
| in_progress | 이동 없이 정지 → 관절·그리퍼·현장 상태 읽기 → 사전 검증 경로만 복귀 → RESULT_UNKNOWN 절차 → 새 집기 금지(재확인 후 B1 절차) |
| motion_unknown | 위와 동일하게 이동 없이 정지·재관측. **기록된 시도는 한 번만 소비**한다. 복구 후 **B3 공통 분기에 따라** 성공·실패 통보·다음 시도·복구 대기 중 하나로 이동한다. 소비된 횟수와 실제 하강 시작 횟수는 로그에 따로 기록 |
| loaded_confirmed 또는 failed_confirmed 중 `clear_committed=true` | **최우선 적용(done_published 분기보다 먼저)**: 안전 위치 재확인 → 결과·clear 재전송 → CAR_LEFT_CONFIRM만 수행. 모순된 플래그 조합(예: clear_committed=true인데 done_published=false)은 HW_FAULT |
| loaded_confirmed | 새 물리 시도 금지. **`done_published=false`이면 정상 경로와 같은 순서로**: 검증된 중간 후퇴(RETREAT_MID) 상태에서 done 발행 → 저장 → 대기 자세 → clear(관절 재확인 후). `done_published=true`이면 사전 검증 경로로 대기 자세 → clear → CAR_LEFT_CONFIRM → idle. 결과 발행에 ack 대기 없음 |
| failed_confirmed | **재집기 금지.** loaded_confirmed와 같은 순서(done_published 기준)로 실패 결과 전달 + 안전 복귀 + clear + CAR_LEFT_CONFIRM → idle |
| 파일 누락·손상·알 수 없는 상태 | **idle로 취급하지 않는다.** 기록은 **이중화(A/B 번갈아 저장 + 체크섬 + 추가 전용 로그)**로 보존하며, 모든 저장에는 **증가하는 순번(seq)**을 붙이고, 저장 완료 기준은 "임시 파일 작성 → 디스크 반영 → 원자적 교체 → 같은 seq를 추가 전용 로그에 기록"이다. 부팅 시 유효한 파일 중 최대 seq를 택하고 **로그의 마지막 seq와 비교**한다(**두 seq가 다르면 어느 방향이든**, 즉 로그 seq가 더 크면 최신 확정 상태를 잃은 것이고 파일 seq가 더 크면 교체 후 로그 기록 전에 중단된 것이므로 재시도 없이 안전 중단. **파일 교체와 로그 기록이 모두 디스크에 반영된 뒤에만 저장 성공을 반환**하며 그 전에는 물리 동작·clear 발행을 허용하지 않는다). 복구 대상은 색·횟수뿐 아니라 **status, 완료 결과, done_published, clear_committed를 포함한 전체 작업 기록**이며, 최신 확정 상태(loaded/failed_confirmed, clear_committed)를 신뢰할 수 없으면 **재시도하지 말고 안전 중단**한다. 0이나 임의 횟수로 초기화해 진행하지 않는다. 최초 설치 시 배포 절차가 만든 idle 파일만 정상 |

**clear 전송 전에 안전 위치를 확인한 뒤 `clear_committed=true`를 영속 저장**한다. 이후에는 전송 여부가 불명확해도 재작업은 하지 않고 안전 위치 확인과 clear 재전송만 수행한다(`clear_committed=true`이면 어떤 재시작에서도 물리 시도 금지). 출발 전 결과 정정 경로는 없다.
### D10 경기 중 구성
경기 중 개발 노트북·원격 접속·외부 모니터링 연결을 끊고 팀 전용 DOMAIN_ID의 두 Pi만 통신. 구성은 경기 전 확정, 경기 중 수정 금지.

## E. 검증 (제한된 검증, 무감점 보장 아님)
- **감지·색 시험(짧은 사이클, 동작 없음)**: 색 2 × 조명 4 × 정지 오차 3 × 20 = 480회(회당 약 10초, ≈ 1.5시간). 공통 검출 로직을 고치면 다른 색·조건도 재시험.
- **전체 동작 사이클 100회**: 위 조건에 배분(색·조명·오차 균등). 치명 이벤트(오색 공, 거짓 ok, 중복 상차, 충돌, 출발 허가 오류) 0건. 1차 성공 ≥ 95%는 하한이며 모든 실패 원인을 분석·수정 후 재시험.
- **실제 코스 완주 20회**: 주차 완료 시 공 이탈 0건 목표, 1건이라도 나오면 원인 수정 후 재시험.
- **규정 위반을 유발하는 중단 지점 시험(지정 시험)**: (1) 시도 기록 저장 직후·하강 전 전원 차단 (2) 그리퍼 열기 직후 재시작 (3) 3번째 시도 결과 불명 (4) done 수신 후 자동차 재시작 (5) 저장 중 손상·정전 (6) ack 유실 (7) 3차 실패 통보 후 재시작 (8) **세 번째 시도 성공 → 완료 저장 → 재시작 → clear 전 공 이탈**(네 번째 시도가 생기지 않는지, color·attempts가 유지되는지) (9) 완료 저장 직후·done 최초 발행 전 중단(순서: done → 대기 자세 → clear 유지) (10) 자동차 재시작 시 저장된 release_allowed가 즉시 실행되지 않는지 (11) 부팅 식별자 변경 후 오래된 clear 거부 (12) `clear_committed` 저장 직후·전송 전 중단 (13) clear 전송 직후 중단 (14) done 발행 후 공 이탈 관측 시 결과를 바꾸지 않고 기록만 하는지. (15) **clear 저장 후 최신 파일 손상 → 이전 정상 파일 복구 시 로그와 seq 불일치를 감지해 안전 중단하는지** (16) 공 복구 대기에서 팀원이 공을 찾지 못하는 경우(시간 종료 → 안전 중단) (17) 공이 바구니 내부에 가려진 경우(복구 대기 중 공통 성공 검사로 성공 확인). 로그에는 **"최종 상차 확인 실패"와 "확정 이후 공 유지 실패"를 구분해 기록**한다(실제 감점 판단은 심판). **먼저 모의 동작(`SOARM_PORT=fake`, 가짜 메시지)으로 횟수·메시지 처리를 확인하고, 필요한 것만 저속 실물로 시험.** 전체 반복 횟수 확대보다 이 지점 검증을 우선.
- 저장 이미지 시험: 서로 다른 촬영 세션, 불확실 처리 비율과 판독 시간 기록(전부 "불확실" 처리하는 우회 금지).
- 일정(사람 시간 포함): 사이클 100회 ≈ 6~8시간(공 재배치·냉각·분석 포함), 완주 20회 ≈ 2~3시간, 감지 480회 ≈ 1.5시간.

## F. 구현 우선순위 [변경] — 규정 처리를 먼저
1. **작은 전체 흐름을 처음부터**: 시도 3회 제한, 작업 파일, 출발 잠금(clear), 기본 과열 중단, 부팅 구분, try/finally.
2. 대기 자세·도착 감지·색 판정.
3. 집기·넣기·확인.
4. 통신 handshake 완성(ack, 재전송).
5. 복구(공 원위치) 자동 재개, 성능 개선.
범위 축소: 지원하는 시작 자세·관측 자세·복구 범위를 좁힌다. 규정 처리 기능을 선택 기능으로 미루지 않는다.

## G. 1일 차 실물 확인
센서 가용성(온도/부하/위치), 허용 한계, 카메라 시야(대기·관측·복구 자세별), 바구니·포스트잇 실제 크기, 고정 자세 허용 오차, 허용 시작 자세, 복구 대기 자세에서의 가시 영역. 각 항목에 "없으면 대안"을 적는다.

## H. 확정 기본값 (사용자가 정한 실행 정책, 규정 문구에서 벗어나지 않는 보수적 해석)
- 색 판정: 티칭한 기준색 중 가까운 쪽 강제 선택(판정 불가 상태 없음).\n- 결과 불명: 사용자 확정 정책에 따라 해당 시도를 실패로 센다(단 B3의 공통 성공 판정을 먼저 수행). 3번째 실패면 실패 통보 후 공 없이 출발.\n- 시도 기록 직후 동작 여부 불명(`motion_unknown`): 그 시도는 소모된 것으로 센다.\n- 놓기(그리퍼 열기) 후 다시 집거나 넣는 동작: 새 시도.\n- 추가 ROS 메시지(`done`, `clear`, `ack`, `state`): 두 Pi 사이 ROS2 통신이므로 규정 9(허용)에 포함되는 것으로 보고 사용.\n- 전원 투입: 휴식(접힌) 자세에서 켜고 자동으로 대기 자세로 이동.\n- 고장·ABORT: 사람 지시 없이 정지 유지, clear 미발행.\n- 바구니 구조는 변경하지 않음. 비상정지는 물리 전원 차단만 사용(원격 명령 없음).\n- 위 기본값은 사용자가 정한 실행 정책이며 규정이 명시한 계산 방식이 아니다. 코드·시험·기록에 그대로 반영하고, 규정 문구와 충돌하는 동작은 만들지 않는다.
